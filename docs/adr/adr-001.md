# ADR-001　在轻量监管法规场景下采用 NumPy 内存点积与内存 BM25，替代独立向量数据库

## 背景
语料为两部香港证监会法规，切块后共 498 个条款级单元。
全规格配置下向量规模为 498 × 1024 维 float32，约 **2.0 MB**；
轻量档 498 × 384 维约 **0.75 MB**。关键词检索侧的倒排索引量级与之相当。
项目早期曾规划以 pgvector 承载向量检索、以 Postgres `tsvector` 承载全文检索。

## 决策
向量检索以 **NumPy 内存点积**实现（向量 L2 归一化后，相似度即单次矩阵乘）；
关键词检索以 **内存 BM25（rank_bm25 Okapi）** 实现。
不引入 pgvector、Elasticsearch 或任何托管向量服务。

## 理由
**① 规模决定架构。** 2 MB 量级的向量全部驻留内存，单次全量点积在 1 vCPU 上耗时低于毫秒级；
近似最近邻索引（HNSW/IVF）的存在意义是在百万级向量上以召回率换延迟，
在 498 条上它只会引入召回损失而没有任何延迟收益。

**② 延迟构成的真实分布。** 实测单查询 p50 延迟中，
轻量档 31.57 ms、全规格档 446.66 ms，其中绝大部分是**查询文本的编码耗时**，
检索本身（点积 + 排序）不构成瓶颈。引入外部向量库无法改善主要矛盾，
反而新增一次网络往返。

**③ 冷启动与零运维。** 内存方案无需建库、无需迁移、无需维护连接池与扩展版本，
进程启动即可用；评测的分阶段独立进程架构（ADR-006）也要求各阶段能独立冷启动，
外部有状态依赖会与该设计冲突。

**④ 部署复杂度与可审计性。** 整条检索链仅依赖 Python 标准库、NumPy 与 rank_bm25，
可在内网离线环境完整复现；审计方无需理解数据库 schema 即可核对检索逻辑。
对金融机构而言，可审计性本身即为交付要求。

## 后果
本方案的适用边界明确：**语料规模增长至十万级切块时，内存点积的线性扫描将成为瓶颈**，
届时应切换至带 ANN 索引的向量库，并重新评估召回率损失。
本基准不提供该规模下的实测数据。
另需注意：内存方案不具备跨进程共享索引的能力，
多副本部署时每个副本需各自持有一份向量，内存占用随副本数线性增长。
